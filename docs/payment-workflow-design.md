# 订单收款单与付款凭证审核设计

日期：2026-09-11。状态：首个可用实现已完成，并已通过独立代码审查。

本文件记录用户已确认的需求与拟定实现，不替代 CONTEXT.md 中当前已上线的业务定义。

## 1. 已确认的业务契约

- 沿用现有销售流程：创建销售单 → 确认订单 → 创建收款单。不从 Privnote 自动创建或确认订单。
- 仅给已确认／已出库、未收款订单生成链接；金额与商品来自正式销售单，一单一次全额 CNY 收款。
- 每张收款单使用一个收款方式，可以选择常用配置，也可以上传本次临时二维码或填写临时账号。
- 临时信息不进入 PaymentMethod 常用配置列表；内部保留交易使用的资料快照。暂不增加“保存为常用”快捷入口。
- 收款二维码和链接共用同一个有效期；付款流程需要允许有效期内反复访问，禁用阅后即焚及访问次数上限。
- 客户免登录上传一张或多张付款截图，不要求另填金额、付款时间或交易流水号。
- 工作人员在订单列表进入审核，只核实一次；核实通过后，按整单金额记入指定人民币资金账户。实际服务商换汇／手续费／结算不在本次建模。
- 截图提交不代表正式到账，不改账户余额、履约状态或库存；正式收款调用既有业务命令。
- 链接到期限制公开访问，内部凭证和审核历史继续保留。

## 2. 当前实现与影响范围

- `frontend/src/components/sales/SalesOrderWorkbench.tsx`：ReceiptPanel 位于商品和利润之后，在受限滚动区内展开创建表单；默认阅后即焚。订单顶部另有直接登记收款动作。
- `frontend/src/pages/PrivnotePage.tsx`：另一处创建入口，字段与订单入口重复，必须共享后续收款表单及规则。
- `frontend/src/pages/PrivnoteViewPage.tsx`：已有付款步骤文字，尚无客户提交凭证的实现；当前订单已收款时直接关闭链接。
- `privnote/views.py`：创建时必选 PaymentMethod，保存配置快照；同一订单只允许一个可访问收款链接。
- `cigars/sales_accounting.py`：receive_sales_order_payment 已实现整单 CNY 收款、账务入账、幂等和账户校验。
- `cigars/services.py`：订单列表／详情序列化收款链接和正式收款事实。

## 3. 页面方案

### 订单内入口

- 订单列表增加“待核实”筛选及数量，订单行显示该提示，但保留原有履约／收款状态标签。
- 选中订单后，首屏紧接订单标题展示收款卡：应收金额、付款进度及一个当前主要动作。
- 尚无链接：创建收款单；有有效链接：复制链接；有待核实凭证：核实收款；已收款：查看收款记录。
- 商品、成本、利润和历史信息继续在详情中展示，不改整个销售工作台布局。
- 原顶部“登记收款”归入收款区的次级动作，保留无客户上传凭证也能登记实际到账的既有能力。存在待审核提交时引导走审核入口，避免跳过待处理记录。
- 前端在切换订单、关闭再打开面板时按订单 ID 重置或隔离草稿，避免把上一单的账号、文件、链接带到下一单。

### 创建面板

- 桌面独立宽面板：左侧填写收款信息，右侧客户预览；手机全屏单列，底部保留主要操作，表单区域滚动。
- 顶部固定显示订单号、客户与整单应收，金额和商品只读。
- 第一层：“本次临时／常用方式”，按用户常用流程暂定默认本次临时。
- 临时方式：微信／支付宝／银行卡；微信支付宝至少有文字账号或二维码；银行卡填写银行名、卡号和户名。
- 二维码支持文件选择、桌面拖放与图片粘贴；预览、替换、移除，失败时保留其他表单内容。
- 临时方式必须明确选择启用中的 CNY 入账账户；常用方式继承其绑定账户。多个候选时不静默选第一项。
- 常用方式以卡片展示类型、内部标签、账号尾号／二维码缩略图和绑定账户，用户明确选择后展示完整预览。
- 收款说明归本张收款单。常用配置的 PaymentMethod.remark 继续属于配置，不能通过本表单编辑；订单备注也不被覆盖。
- 有效期沿用 1/6/24/72/168/720 小时，默认 24 小时。可选密码收纳到“更多设置”，无阅后即焚和次数限制。
- 客户预览严格白名单：不显示内部账户、配置标签、服务商名称、审核备注或后台状态字段。
- 生成成功后面板保留成功视图、明确的“复制链接”和“查看客户页”按钮。等待用户主动复制，复制失败提供可手动选取的链接，不假报成功。
- 请求超时可用原幂等键重试；服务端返回已有有效链接时转为链接展示，而非让用户重新填写。

### 客户页

- 延续 Light 主题与 StoreHeader，展示商品／金额／收款方式，支持二维码放大和银行账号复制。
- 提交前可选择多张截图、查看缩略图和移除；提交按钮在至少一张有效图片时可用。
- 提交成功显示“付款凭证已提交，等待核实”，隐藏继续付款引导；不得用“已到账”或“付款成功”代替待审核。
- 需补充时展示工作人员给客户的说明，并允许重新提交；原提交和图片留在历史中。
- 已收款时，在链接有效期内显示到账确认结果，隐藏二维码及上传入口。到期后统一显示过期，不泄露交易详情。
- 图片上传或网络失败保留选择并允许重试；用户返回页面时从服务端恢复状态。

### 审核面板

- 从订单列表／收款卡进入，集中展示当前截图、历史提交、金额、绑定入账账户、提交时间。
- 图片缩略图可放大；手机底部固定审核动作，键盘可关闭放大层和面板。
- “确认到账”提交整单金额、业务日期和当前提交 ID，沿用既有工作人员权限和业务日期约定。
- “需补充凭证”要求填写面向客户的原因；客户再次提交形成新记录，不覆盖旧审核结果。
- 审核成功显示正式收款编号与业务日期；出库／待出库状态保持原样。
- 提交到期不影响工作人员审核。账户停用、订单取消、金额不一致时必须明确阻止入账并保留待处理证据。

## 4. 模型提案：两张新表，位于 privnote/models.py

### PaymentSubmission：一次客户付款声明及其审核

| 字段 | 拟定用途 |
| --- | --- |
| sales_order | 必填 FK → cigars.SalesOrder，PROTECT；按订单查询和约束并发 |
| privnote | 必填 FK → Privnote，PROTECT；绑定此次提交实际使用的链接／快照 |
| amount_cny | Decimal，服务端从销售单冻结应收复制；不接受客户输入金额 |
| fund_account | 必填 FK → accounting.FundAccount，PROTECT；从本单内部配置取值 |
| status | pending / needs_more / accepted / closed |
| submitted_at | 服务器接收提交时间 |
| reviewed_by / reviewed_at | 人工审核者与时间；pending 时为空 |
| review_note | 需补充原因；不可用来修改正式会计事实 |
| closed_reason / closed_at | 订单取消、其他入口已入账等导致无法继续审批时的系统关闭记录 |
| sales_receipt | 可空 OneToOne → cigars.SalesReceipt，PROTECT；仅 accepted 有值 |
| idempotency_key / request_hash | 匿名提交重放凭证，按收款单作用域唯一；哈希包含图片内容摘要 |

sales_order 与 privnote.sales_order 的一致性由命令层在同一事务中校验；数据库无法用普通 CheckConstraint 跨表比较。不向客户端开放这两个关联字段的自由赋值。

约束提案：同一订单最多一条 pending、最多一条 accepted；amount_cny > 0；accepted 必须有审核人、审核时间和 SalesReceipt；needs_more 必须有审核人、时间及非空说明；pending 不得提前关联正式收款。

终态记录不重新打开：needs_more 后再次上传创建新的 pending；accepted 永远保留，即使之后订单退款也不回写此审核记录。closed 保留关闭原因，不伪造人工拒绝。正式收款／取消命令的协调层关闭不再可审批的 pending，并写订单事件。

### PaymentAttachment：本次提交的一张截图

| 字段 | 拟定用途 |
| --- | --- |
| submission | FK → PaymentSubmission，PROTECT |
| file | 使用私有存储的图片文件，不能被公共 /media/ 静态路由直接访问 |
| original_name / content_type / size | 文件展示与已验证元数据 |
| sha256 | 去重／请求摘要；不单独等同于付款身份校验 |
| sort_order / created_at | 展示顺序及保存时间 |

图片至少一张由提交命令保证：整个请求验证成功并保存全部图片后才建立完整提交；不能创建无附件的 pending。提交后不提供原地替换／删除附件接口。

### 现有模型

- SalesOrder、SalesReceipt、LedgerTransaction、FundAccount、PaymentMethod 暂不新增字段或改变枚举；pending 提示从 PaymentSubmission 派生。
- Privnote 的 data_json 使用显式 schema_version=2，并记录 payment_source=saved/temporary、收款展示快照、内部入账账户 ID；对新旧格式显式分支，不能靠 payment_method_id 是否存在猜格式。
- 保存二维码使用随机私有对象键，由受控图片接口访问；不新增 PaymentMethod 记录，不复用历史 sales_order.payment_manual 写入路径。
- 生成时保存内部账户 ID 和名称快照，提交／审核时再校验真实账户。名称仅作追溯展示，不决定入账归属。
- 原有配置二维码可能是公开媒体文件，不能声称已获得私有隔离；为新链接复制到受控快照存储，旧链接访问路径按兼容策略保留。

## 5. 状态、幂等与事务

1. 创建收款单：工作人员权限 → 校验幂等 → 锁定订单 → 校验可收款状态及无有效链接／pending → 校验账户与收款资料 → 保存不可变快照与链接。只展示，不触发库存动作。
2. 客户提交：验证链接 token、可选密码会话和有效期 → 验证请求大小／图片并计算摘要 → 锁定订单 → 优先返回同键同内容的已有提交 → 仅对新请求校验订单状态、当前快照及无 pending → 建立 pending 及附件。相同键不同内容返回冲突。匿名成功重试仍受链接有效期约束，到期后不得借幂等读取私有信息。
3. 审核通过：验证工作人员及真实操作人 → 锁定订单和 submission → 优先进行同操作人同参数的幂等重放 → 仅对新操作重检 pending、金额、账户、订单状态 → 调用 receive_sales_order_payment → 关联 receipt、写审核和订单事件 → 共同提交事务。重放不能因首次成功已经将状态改成 accepted/paid 而失败。
4. 需补充：锁定相同资源，先处理同操作人同参数幂等重放，仅对新请求验证 pending 并记录审核意见，不生成收款。
5. 并发审核／直接登记收款／取消订单使用同一订单锁顺序及项目 SQLite writer gate；数据库唯一约束兜底。失败时审核和账务全部回滚。
6. 正式写入沿用 IdempotencyRecord 与 AgentContext，保留操作人、业务日期、Agent 来源和命令信息。匿名上传单独使用 Submission 幂等信息，不制造工作人员身份。
7. 链接到期后若有 pending，先核实原凭证再决定下一步，不能为了重新生成链接而丢掉待审核记录。needs_more 且旧链接已过期时，可为原订单重新生成链接，内部保留全部历史。
8. 前端生成成功视图与订单刷新分离，避免刷新使 canCreateLink=false 后成功视图立刻卸载；晚返回的异步响应不能污染另一个订单。
9. 收款／取消协调必须覆盖所有实际调用入口：sales_api.sales_order_receive、agent_api.receive_sales_order_payment_command，以及 sales_api 和 agent_api 对 cancel_confirmed_sales_order 的调用；不能只改 Web 视图或旧 cancel_sales_order 包装器。拟集中到一个业务协调服务，复用底层正式收款命令并处理提交终态，禁止各入口复制关闭逻辑。
10. 审核调用协调服务时，当前 submission ID 必须是服务端授权并锁定的对象；正式收款成功后该条标记 accepted。直接登记收款则将遗留 pending 标记 closed（其他入口已入账）。不能先统一关闭全部 pending 再尝试审核通过；取消时统一关闭可审批提交且保留截图。所有状态变化与对应正式动作处于同一事务。

## 6. API 与文件边界（路径提案）

- POST /privnote/create/：扩展临时方式与创建幂等；保留旧常用配置请求兼容。
- GET/POST /api/privnote/:token/：保持查看／密码验证入口，返回白名单付款流程状态。
- POST /api/privnote/:token/payment-submissions/：multipart 截图提交；token 授权，可选密码验证必须传递到提交和图片请求。
- GET /api/privnote/:token/payment-images/:opaque_id/：只访问当前链接允许的二维码／凭证，不允许任意文件路径、任意 URL 或跨单读取。
- 工作人员审核通过／需补充接口放在 sales API 订单作用域下；业务实现位于 privnote/services/payment_submissions.py，复用正式收款命令。
- 订单 API 增加轻量 payment_review 摘要，列表不携带图片地址或完整快照；详情／审核接口按权限读取附件。
- 新公开接口设置请求数量／体积限制、真实图片解码校验、随机文件名及缓存禁用；工作人员写接口遵守 CSRF 和现有认证规则。
- 初步工程限额：1–5 张，每张至多 5MB，JPEG/PNG/WebP，总体积至多 25MB；前后端与反向代理限制统一，拒绝图片解压炸弹。此为拟定技术默认值。
- 浏览器预选文件用对象 URL，本地预览不先创建公开附件；一次 multipart 提交，失败仅清理本次新写入且未被数据库引用的文件，保留重放请求已成功保存的文件。
- SQLite 事务不会回滚文件系统：需要失败补偿及孤儿文件清理策略，不能只依赖 transaction.atomic。

## 7. 兼容与迁移策略

- 首次迁移只新增 PaymentSubmission、PaymentAttachment 和相关约束／索引，不回填历史付款凭证、不重算历史收款、不修改生产余额。
- 历史链接没有 submission 时继续呈现原有信息；不伪造“未上传所以未付款”的历史事实。
- 新付款链接强制可重复访问；旧阅后即焚链接不静默延长权限。需要新流程时在原链接失效后为合格订单生成新链接。
- 对新格式链接：已收款优先呈现成功态而非笼统 closed；退款／取消显示对应终态并隐藏付款操作。有效期检查仍先于公开详情返回。
- 全局 Privnote 创建入口和订单创建入口共用表单与请求组装；管理常用方式功能继续独立。
- 实现获准后再更新 CONTEXT.md 的付款凭证、审核和临时方式定义，并明确旧 ADR 0015 已与当前双状态代码不一致；设计稿不把旧 ADR 的“收款即出库”带回实现。
- 不自动 push、部署或运行生产迁移。设计批准不等于生产变更批准。

## 8. 验收与实施切片

1. 设计确认：OpenDesign 交互原型覆盖桌面／手机的创建、复制、上传、审核、成功、需补充和过期。
2. 收款单创建：临时与常用快照、受控二维码、共享表单、幂等、订单顶部入口；测试无库存或账务副作用。
3. 凭证提交：模型／私有附件／匿名授权／状态恢复／错误重试；测试越权、过期、密码、无图、假图片、过大、重放及跨订单隔离。
4. 人工核实：订单待核实筛选及面板，审核与正式入账事务；测试并发审核、重复确认、直接收款竞争、取消竞争、账户停用、金额不符和账务／提交协调失败整体回滚。覆盖成功响应丢失后的重试、上传后已经审核再重试、同键不同内容冲突、已到期公开重放仍拒绝。
5. 兼容与集成：旧链接、直接登记收款、补传历史、退款后审核历史、有效期内成功页；检查创建后成功视图以及切换订单竞态。
6. 本地明确 DJANGO_DEBUG=True：目标 Django 测试、manage.py check、迁移一致性检查；前端 typecheck/lint、关键交互测试和构建。新模型和正式收款接入完成后进行独立风险审查。
