# 收款单付款凭证上传与自动关闭设计

## 背景

当前收款单由 staff 在 React SPA `/privnote/` 创建，客户通过公开路由 `/p/:token/` 查看。收款单关联一张 `SalesOrder`，创建时订单状态为 `pending_payment`。现有 Privnote 的销毁语义由查看次数和有效期控制，客户不能上传付款凭证，也没有将凭证与销售单放在一起核验的入口。

本功能把收款单的“阅后即焚”触发点改为付款凭证提交：客户在有效期内可反复查看待付款收款单；成功提交截图后，订单自动变为已付款，链接立即关闭。店员核验后可以修改订单状态；只有改回待付款才重新开放原链接，且已过期链接永不重开。

## 目标

- 客户可从收款单页面一次提交 1–3 张付款截图。
- 提交前允许本地预览、删除和替换图片，并要求最终确认。
- 凭证保存与销售单变为 `paid` 作为一次一致的业务操作完成。
- 上传成功后立即关闭收款单，并给客户明确的成功反馈。
- 店员可在销售单后台查看所有历史提交并修改销售单状态。
- 错误凭证被发现后，店员把订单改回 `pending_payment` 即可重新开放未过期链接。
- 创建收款单时可选择是否展示固定三步付款引导；默认不展示。
- 付款截图使用私有存储，只允许 staff 查看。

## 非目标

- 不增加 OCR、自动识别金额或自动判断截图真伪。
- 不增加独立的“凭证审核中/通过/驳回”状态机。
- 不发送短信、微信或邮件通知。
- 不允许客户在提交成功后查看或下载已上传的图片。
- 不改变库存、消息或批发报价类型的阅后即焚逻辑。

## 已确认的产品决策

- 每次提交至少 1 张、最多 3 张图片。
- 支持 JPG、PNG、WebP；每张最大 10MB。
- 上传成功后自动把关联销售单状态改为 `paid`。
- `pending_payment` 是唯一开放收款链接的订单状态。
- `paid`、`shipped`、`completed` 均关闭链接；`cancelled` 关闭链接并显示订单已取消。
- 改回 `pending_payment` 时，如果 Privnote 尚未过期，原链接重新开放。
- Privnote 一旦过期即永久失效，修改订单状态不会重开，必须新建收款单。
- 每次重新提交都建立新的凭证记录，旧截图保留。
- 固定引导采用上传区前的纵向说明卡片，文案为：
  1. 核对订单金额。
  2. 按页面中的收款方式完成付款。
  3. 上传付款截图，提交后链接自动关闭。

## 数据模型

### Privnote

新增字段：

- `show_payment_guide: BooleanField(default=False)`：仅收款类型使用。创建请求未提供该参数时保持 `False`。

收款类型的可访问性不再由 `view_count >= max_views` 决定。对收款单使用以下顺序判断：

1. 超过 `expires_at`：已过期，永久不可访问。
2. 没有关联销售单：配置错误，不可提交。
3. 销售单状态为 `pending_payment`：可查看、可提交。
4. 销售单状态为 `cancelled`：已取消。
5. 其他状态：已关闭。

`view_count` 仍可记录查看次数，但不会让待付款收款单在首次查看后销毁。库存、消息和报价类型继续使用原有查看次数逻辑。

### PaymentProofSubmission

表示客户的一次完整提交：

- `privnote`：关联来源收款单。
- `sales_order`：关联销售单，作为后台核验入口。
- `client_submission_id`：客户端生成的 UUID，唯一，用于幂等重试。
- `submitted_at`：提交时间。

`privnote` 和 `sales_order` 外键均使用 `on_delete=PROTECT`，防止硬删除破坏凭证历史。项目当前对销售单使用软删除，因此正常业务流不会触发保护异常。

### PaymentProofImage

表示一次提交中的单张图片：

- `submission`：关联 `PaymentProofSubmission`，使用 `on_delete=CASCADE`；删除整次提交时同时删除其图片记录。
- `image`：使用私有文件存储的图片字段。
- `original_name`：客户设备上的原文件名，仅供后台参考。
- `content_type`：后端确认后的图片类型。
- `size_bytes`：文件大小。
- `created_at`：保存时间。

公开 API 和服务层共同保证每个提交包含 1–3 张图片；提交记录只能通过该服务创建。图片文件名使用不可预测的 UUID，不采用客户原文件名作为存储路径。

## 私有文件存储

付款截图可能包含姓名、账号和交易信息，不放入当前可公开访问的 `/media/` URL 空间。

- 新增 `PRIVATE_MEDIA_ROOT = BASE_DIR / 'private_media'`，并把 `private_media/` 加入 Git 忽略。
- 付款截图保存到 `private_media/payment_proofs/YYYY/MM/`。
- `PaymentProofImage.image` 使用无公开 `base_url` 的私有存储。
- 后台预览和原图通过 staff-only Django 响应读取。
- 下载接口根据数据库记录解析文件，禁止接受任意磁盘路径。
- 返回客户的创建、查看和提交响应中不包含凭证文件路径。

## API 设计

### 创建收款单

现有 `POST /privnote/create/` 增加：

- `show_payment_guide=true|false`，默认 `false`，仅在 `note_type=payment` 时保存。

收款单始终采用“提交凭证后关闭”的生命周期。后端对 payment 强制保留阅后即焚语义，但将销毁触发点固定为凭证提交成功；创建页不允许把收款类型改成首次查看后销毁。

### 查看收款单

现有 `GET/POST /api/privnote/<token>/` 在收款数据中增加：

- `show_payment_guide`。
- 足以区分 `pending_payment`、`closed`、`cancelled` 和 `expired` 的状态或错误原因。

待付款时可反复读取。关闭状态使用明确的响应原因：

- 已有凭证且订单已付款：提示“付款凭证已经提交，收款单已关闭”。
- 无凭证但订单已不再待付款：提示“收款单已关闭”。
- 订单已取消：提示“订单已取消”。
- 已过期：提示“收款单已过期”。

### 提交付款凭证

新增公开能力链接接口：

`POST /api/privnote/<token>/payment-proof/`

请求使用 `multipart/form-data`：

- `images`：重复字段，1–3 个文件。
- `client_submission_id`：客户端 UUID。
- `password`：密码保护收款单需要提供。

后端处理顺序：

1. 查询并锁定 Privnote 与关联销售单。
2. 验证类型必须为 payment。
3. 验证密码并校验 `client_submission_id` 格式。
4. 查询同一 `client_submission_id` 的既有提交；若属于当前 Privnote，立即返回原成功结果。
5. 对首次请求验证有效期和订单状态；只有 `pending_payment` 可新建提交。
6. 验证文件数量、单文件大小、允许类型和真实图片内容。
7. 在事务中创建提交记录和图片记录，并通过订单业务服务把状态改为 `paid`。
8. 返回提交数量、提交时间和关闭状态，不返回私有图片地址。

幂等检查先于有效期和订单状态检查，因此同一成功请求即使在响应丢失后遇到订单已付款或链接刚过期，仍返回原成功结果。不同 Privnote 使用已存在的标识时返回冲突。不同标识的并发请求通过订单行锁串行化；第一笔成功后，后续请求看到非待付款状态并返回已关闭。

文件系统本身不参与数据库事务，因此服务层跟踪本次写入的文件；事务或保存失败时删除本次文件，避免半套凭证和孤儿文件。

### Staff 凭证读取

提供只允许 staff 使用的图片读取端点。端点接受凭证图片记录 ID，通过数据库找到私有文件并流式返回；不暴露或接受磁盘路径。缩略图和原图访问都经过相同权限检查。

## React 客户流程

### 创建页

收款 tab 增加“展示付款步骤引导”开关：

- 默认关闭。
- 仅收款类型显示。
- 提交时发送 `show_payment_guide`。

所有 UI、布局和样式改动先更新 `.opendesign/` 原型并验证，再由 Kanban 的 `kimi-coder` 应用到 `frontend/`，遵守项目前端工作流。

### 客户查看页

待付款页面保持现有 Light 主题、StoreHeader、订单和收款方式展示。在上传区域前按条件显示固定三步说明卡。

上传组件行为：

- 可选择或追加图片，总数 1–3 张。
- 选择后只生成浏览器本地预览，不提前上传临时文件。
- 可删除图片并重新选择。
- 前端提前检查数量、类型和大小；后端仍执行完整校验。
- “提交付款凭证”按钮打开二次确认。
- 提交期间禁用修改和重复提交，并显示进度或明确的处理中状态。
- 网络或服务端失败时保留当前选择，允许重试。

成功响应后直接显示成功页：

- 标题：“付款凭证已提交”。
- 显示收到的图片数量。
- 告知客户收款单已自动关闭。
- 显示订单状态“已付款”。

刷新或再次访问关闭链接时显示独立关闭页：“收款单已关闭；付款凭证已经提交，无需重复操作。”已取消和已过期使用各自文案。

密码保护收款单在客户验证成功后，由前端保留本次输入密码并随凭证提交请求发送；不把明文密码写入持久化浏览器存储。

## Django Admin

`SalesOrderAdmin` 增加：

- 列表显示订单状态、凭证提交次数和最近提交时间。
- 按订单状态筛选。
- 详情页按提交时间分组展示凭证缩略图，点击通过 staff-only 端点查看原图。
- 保持 `status` 可编辑。改回 `pending_payment` 后，未过期的关联收款链接自动重开。

凭证记录作为审计历史只读展示，不提供图片替换。Privnote 后台继续显示链接与关联销售单信息，但不是日常核验入口。

## 错误处理

- 0 张或超过 3 张：拒绝整个请求。
- 非 JPG/PNG/WebP、伪造 MIME、损坏图片或单张超过 10MB：拒绝整个请求。
- 密码错误：不保存文件，不改变状态。
- 链接过期：返回过期原因，不因订单改回待付款而恢复。
- 订单不是待付款：返回已关闭或已取消原因。
- 网络中断但服务端已成功：客户端使用同一 `client_submission_id` 重试并得到原成功结果。
- 任意数据库或文件保存错误：不修改订单状态，清理本次文件并允许重试。

## 测试策略

### Django 模型与服务测试

- `show_payment_guide` 默认值为 `False`。
- 收款单待付款期间多次查看仍可访问；其他 Privnote 类型保持旧销毁行为。
- 收款单过期后永久不可访问。
- 状态映射只允许 `pending_payment` 开放。
- 私有文件路径不出现在公开 API 响应中。

### Django API 集成测试

- 创建请求默认关闭引导，显式开启时查看响应包含开启状态。
- 1 张和 3 张合法图片提交成功。
- 0 张、4 张、超限、损坏和伪造类型图片全部失败且无副作用。
- 密码保护、过期、取消和非待付款状态拒绝提交。
- 成功提交创建一组完整凭证、订单变为 `paid`、链接关闭。
- 改回 `pending_payment` 后链接重开并可再次提交，旧记录保留。
- 同一提交标识重复请求幂等。
- 不同标识并发请求只允许一组成功。
- staff 可以读取凭证；匿名和普通用户不能读取。
- 模拟图片保存失败时数据库和订单状态回滚，已写文件被清理。

### React 测试与验证

- 创建页引导开关默认关闭并正确提交布尔值。
- 条件开启时渲染固定 B 方案三步卡。
- 文件数量、类型和大小校验。
- 本地预览、删除、替换和二次确认。
- 提交中禁用重复操作；失败后可重试。
- 成功页、已关闭、已取消和已过期状态文案。
- 密码随提交请求发送但不写入持久化存储。

实施完成前执行相关 Django 测试、前端测试、TypeScript/Vite 构建、迁移检查和完整回归测试。

## 迁移与兼容性

- 新增 Privnote 布尔字段和两张凭证表，不修改现有历史收款数据。
- 历史收款单默认不展示步骤引导。
- 历史待付款收款单采用新的“提交后关闭”访问语义；已过期记录仍保持失效。
- 库存、消息和报价类型的 API 与销毁行为保持兼容。

## 验收标准

1. staff 创建收款单时可选择步骤引导，默认关闭。
2. 客户可在未过期、待付款的收款单中预览并提交 1–3 张合法图片。
3. 成功提交只产生一组完整凭证，订单自动变为已付款，客户收到明确成功反馈。
4. 关闭链接再次访问时显示明确关闭原因，而不是通用错误。
5. 店员能在销售单后台安全查看所有历史截图并修改订单状态。
6. 订单改回待付款后，未过期链接重新开放；过期链接永不重开。
7. 凭证文件不通过公开媒体 URL 暴露。
8. 重复、并发、非法文件和中途失败均不会产生重复记录、半套数据或错误订单状态。
