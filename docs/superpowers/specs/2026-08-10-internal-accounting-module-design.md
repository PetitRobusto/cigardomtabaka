# 内部经营管理账模块设计

- 日期：2026-08-10
- 状态：对话设计已确认，等待书面规格复核
- 基准货币：人民币（CNY）
- 业务日期默认时区：莫斯科（Europe/Moscow）

## 1. 背景

CigarDomTabaka 以卢布采购雪茄，以人民币销售，并频繁在人民币、USDT 和卢布之间转换经营资金。人民币由两位合伙人分别保管在两个公司专用账户中；卢布使用一个公司专用银行卡账户；USDT 使用一个独立公司账户。账户保管人不拥有账户中的公司资金。

现有系统已经具备采购单、采购批次、销售单、FIFO 分配和部分利润字段，但存在四个与本需求直接相关的边界问题：

1. 采购人民币成本来自采购单上的手填汇率，无法与实际换汇及外币余额核对。
2. `SalesOrder.status` 混合了付款与履约状态，现有 `confirm_payment()` 同时确认付款和出库，不符合通常先出库后收款、偶尔预收的业务。
3. Privnote 收款文档当前会创建销售单，临时客户文档被错误地当成销售事实来源。
4. 库存按支数聚合，FIFO 未把包装规格纳入匹配，也无法可靠区分完整盒与拆盒后的散支。

本设计建立内部经营管理账，不承担中国或俄罗斯的法定会计、税务申报或正式财务报表职责。

## 2. 目标

系统必须能够回答：

- 每个人民币、卢布、USDT 公司账户有多少原币。
- 每个外币账户当前余额承载多少人民币账面成本。
- 公司有多少应收款、客户预收款、在途采购和库存成本。
- 每笔已出库销售的 FIFO 成本、商品毛利和订单贡献利润。
- 每个自然月的收入、成本、费用和人民币经营净利润。
- 公司累计形成和已经分配了多少利润。
- 任意余额或利润数字由哪些不可覆盖的业务流水形成。

## 3. 一期不做

- 法定会计、税务申报和正式财务报表。
- 银行、微信、支付宝或交易所自动同步。
- 自动市场汇率、外币市场估值和未实现汇兑损益。
- 分期收款、采购分批付款和采购分批到货。
- 卢布换回人民币。
- 已履约销售的完整退货流程；已预收但未履约订单的退款属于一期。
- 自动决定或强制执行分红比例。
- 多公司、多仓库和复杂角色权限。

## 4. 已确认的业务原则

### 4.1 公司资金与权限

- 所有受管账户只保存公司资金，不混入个人收支。
- 初始账户为两个人民币账户、一个卢布账户和一个 USDT 账户。
- 底层允许未来增加同币种账户；外币成本始终按账户独立计算。
- 两位合伙人拥有相同的查看和记账权限，并能查看全部公司账户。
- 每笔操作保存操作人、业务日期、真实创建时间和更正关系。

### 4.2 基准货币与外币成本

- 所有库存成本和经营结果以人民币衡量。
- 每个外币账户同时保存原币余额和人民币账面成本。
- 外币移动平均成本等于该账户人民币账面成本除以原币余额。
- 人民币和既有 USDT 是换入卢布的并列来源，不固定经过“人民币 → USDT → 卢布”。
- 换汇只记录实际转出和实际到账，不单列手续费，不使用市场汇率重估，也不产生利润。
- 同币种账户转账时，原币和其按转出账户移动平均计算的人民币成本一同转移。

### 4.3 业务日期与月报

- 每笔业务保存显式业务日期，默认使用莫斯科当天日期。
- 允许按真实业务日期补录。
- 月报按业务日期的自然月汇总，不依赖服务器创建时间。
- 每笔已入账交易获得不可变的 `effective_sequence`；成本计算与缓存重建统一按“业务日期、有效顺序”排序，同一业务日期按有效顺序确定先后。
- 初次启用和历史补录完成前，所有补录先作为草稿；启用后，影响外币移动平均的交易若早于该账户已有后续交易，不允许直接插入已入账链。
- 确需补录或更正上述历史交易时，系统必须建立受控的反向与重放链，按同一确定顺序重建所有受影响交易；不得只改一笔旧流水或静默覆盖后续成本。

### 4.4 不可覆盖流水

- 草稿可编辑。
- 已入账交易不直接覆盖或删除。
- 更正通过反向流水与替代流水完成。
- 如果历史外币交易已经被后续采购或费用使用，更正必须连同受影响链路由系统引导处理，不能静默重算并覆盖旧成本。

## 5. 架构决策

采用“统一账务流水”，不直接依赖模型余额字段，也不建设要求用户手选会计科目的完整复式总账。

### 5.1 模块边界

| 模块 | 唯一职责 |
|---|---|
| 销售 | 销售单、商品、价格、库存预留、履约和收款状态 |
| 采购/库存 | 采购明细、在途、入库批次、完整盒、散支和 FIFO |
| Privnote | 临时展示收款信息、报价和消息 |
| Accounting | 资金账户、统一流水、费用、分红、对账和月报 |

销售、采购和库存继续拥有业务事实。Accounting 只接收这些业务动作产生的账务结果。业务状态变化与其账务流水必须在同一数据库事务内提交；任一步失败时全部回滚。

### 5.2 统一流水

建议新增以下核心记录：

- `FundAccount`：用户可见资金账户，包含名称、币种、保管人和启用状态。
- `LedgerTransaction`：用户可理解的业务交易，包含类型、业务日期、草稿/入账/已冲正状态、操作人、业务来源和更正关系。
- `LedgerPosting`：交易生成的成对流水，包含资金账户或内部分类、原币金额及人民币账面金额。
- `AccountReconciliation`：账户盘点时的系统余额、实际余额、差异、处理方式和原因。
- `Expense`：经营费用及其付款账户、业务日期和分类。
- `Dividend`：一次分红及两位合伙人的实际金额和转出账户。

内部分类至少包括应收款、客户预收款、在途采购、库存、收入、销售成本、经营费用、未分配利润、期初投入资本和期初未分配利润。用户不需要手工选择这些内部分类。

每笔已入账交易的人民币账面流水必须平衡。页面可使用缓存余额提高读取速度，但不可把缓存当作事实来源；缓存必须能从流水完全重建。

`LedgerTransaction` 必须保存系统级唯一且不可变的有效顺序，由数据库在正式入账时原子分配；草稿不占号，同一业务动作产生的全部流水共享一个有效顺序。切账期初流水必须先于 2026-08-10 当日业务取得顺序。任何余额、外币移动平均、成本分配和月报重建都必须使用相同排序规则。已存在依赖交易时，禁止通过修改业务日期或顺序把新交易插入其前方。

人民币和卢布金额保留 2 位小数，USDT 支持最多 8 位小数；资金、成本、比例和利润计算全部使用精确十进制，不使用二进制浮点数。

## 6. 资金与换汇

### 6.1 换汇表单

用户输入：

- 业务日期。
- 转出账户：人民币或 USDT。
- 实际转出数量。
- 转入卢布账户。
- 实际到账卢布数量。
- 可选备注和凭证。

人民币转出时，到账卢布承接实际转出的人民币金额。USDT 转出时，到账卢布承接所转出 USDT 按源账户移动平均计算的人民币账面成本。成交比例只用于展示。

### 6.2 外币移动平均

- 外币流入后，新账面成本等于原账面成本加本次流入承接的人民币成本。
- 外币流出成本等于流出前移动平均成本乘以实际流出数量。
- 外币余额归零时，人民币账面成本必须同时归零；舍入尾差进入最后一笔流出。
- 外币账户不得出现负的原币余额或人民币账面成本。
- 同一业务日期内的多笔流入、流出严格按不可变有效顺序逐笔计算；批量导入、缓存重建和报表重算不得自行改变顺序。

## 7. 采购与在途

### 7.1 采购明细

采购单按供应商报价录入每款雪茄、包装规格、采购盒数和每盒卢布价格。整单卢布总额等于明细小计合计。

### 7.2 采购状态

```text
草稿 → 支付采购款/在途 → 整单确认到货/已入库
```

- 一张采购单一次性从一个卢布账户付款。
- 支付时按卢布账户当时移动平均成本减少卢布资金，并等额增加在途采购人民币成本。
- 整单人民币成本按各明细卢布小计占比分配，舍入尾差进入最后一条明细。
- 到货一次完成，在途成本转为对应包装规格的库存批次，不重复扣款或计算汇率。
- 一期不提供分批付款和分批到货，确认到货要求全部明细数量与采购单一致。实际少货属于一期外异常，不能通过确认到货伪造库存；到货后发现破损则先正常入库，再使用破损库存调整减少库存并计入当月费用。

## 8. 包装库存与 FIFO

`PurchaseBatch` 继续作为 FIFO 核心，但新库存事实必须明确保存：

- 包装规格 `box_size`。
- 原始完整盒数和剩余完整盒数。
- 同批次散支数量。
- 每盒人民币成本和每支人民币成本。
- 批次原始人民币成本、剩余人民币成本池和累计已结转成本。

每个批次必须始终满足成本守恒：

```text
批次入库人民币成本
= 剩余库存成本池
+ 累计销售成本
+ 累计库存调整成本
```

盒、支的展示单位成本可以舍入，但实际结转从批次剩余成本池计算；批次最后一个库存单位承接全部人民币尾差，确保批次清空时剩余成本池精确归零。拆盒只改变库存形态，不重算或舍入批次总成本。

库存预留按“雪茄 + 包装规格 + 批次顺序”匹配。完整盒销售只占用完整盒，不能把不同批次或不同包装的散支凑成整盒。

拆盒是独立库存动作：一个完整盒减少，同批次散支增加 `box_size` 支，总人民币成本不变。散支销售只从散支库存 FIFO 预留；需要时必须先显式拆盒。

确认销售时只创建预留，不减少物理在库成本。可用库存等于物理在库减活动预留。确认出库时才减少物理库存并把对应成本转为销售成本；出库前取消只释放预留。

## 9. 销售、收款与 Privnote

### 9.1 销售单是事实来源

每笔销售必须创建独立 `SalesOrder`。销售中心是 React SPA 的一等功能，Privnote 不再创建销售事实。

销售单商品默认按完整盒录入，极少数散支销售通过次级入口完成。销售单在草稿阶段允许编辑。确认后冻结商品、包装规格、数量、成交价格、人肉费承担方式和客户人肉费收取金额，不随后续报价表或费用设置变化；需要变更时必须先取消并重建销售单。

### 9.2 两条状态轴

履约状态：

```text
草稿 → 已确认/已预留 → 已出库
                  ↘ 出库前取消
```

收款状态：未收款、已收款、待退款、已退款。

组合显示：

| 履约 | 收款 | 用户状态 |
|---|---|---|
| 草稿 | 未收款 | 草稿 |
| 已确认 | 未收款 | 待出库 |
| 已确认 | 已收款 | 已预收，待出库 |
| 已出库 | 未收款 | 已出库，待收款 |
| 已出库 | 已收款 | 已完成 |
| 已取消 | 未收款 | 已取消 |
| 已取消 | 待退款 | 已取消，待退款 |
| 已取消 | 已退款 | 已取消，已退款 |

合法转换仅包括：草稿确认、已确认出库、已确认取消、已确认未收款整单收款、已出库未收款整单收款、待退款整单退款。草稿不得收款；已出库订单不得取消；已取消订单不得出库或收款；已退款订单不得再次退款。所有非法组合和非法转换必须由后端拒绝，不能只依赖前端隐藏按钮。

### 9.3 销售动作

- 草稿不预留库存、不记账。
- 确认销售按包装 FIFO 预留库存。
- 出库前未收款订单取消时释放预留。
- 出库前已预收订单取消时释放预留并进入待退款；退款金额必须等于该单已收的全部预收款。退款只能从指定人民币账户一次性转出；账户余额不足时拒绝完成退款，订单保持待退款。
- 确认出库时确认商品收入、客户承担的人肉费收入、FIFO 销售成本及应收或预收结转，利润进入出库业务日期所在月份。
- 出库后收款时增加实际到账人民币账户并结清应收，不重复产生利润。
- 提前收款时增加人民币账户并形成客户预收款，不产生收入或利润；出库时再把预收款结转为收入。
- 一张销售单最多一笔整单收款，不支持分期付款。收款金额必须精确等于销售确认时冻结的应收总额；多收、少收均拒绝，差异必须先在销售单草稿阶段解决。

### 9.4 人肉费用

每张销售单最多关联一笔人肉运输费用，实际支出只支持人民币：

- 实际人肉成本。
- 客户是否承担；公司承担时，向客户收取金额必须为 0。
- 向客户收取金额；客户承担时默认等于实际成本，但允许录入与实际成本不同的非负金额，并在销售确认时冻结。
- 实际付款人民币账户、业务日期和备注。

销售单应收总额等于商品金额加向客户收取的人肉费。订单贡献利润等于商品收入、客户人肉费收入减 FIFO 商品成本和实际人肉成本。月利润中的人肉费实际成本按其付款业务日期归属。

### 9.5 PaymentMethod 与 Privnote

- 每个现有 `PaymentMethod` 绑定一个人民币资金账户。
- Privnote 收款单必须从已有销售单生成，只展示订单和付款信息，不改变库存或账务。
- 同一销售单可重新生成 Privnote；Privnote 过期或销毁不影响销售单。
- Privnote 报价单不预留库存、不产生收入或会计流水。
- 报价只能由内部人员人工“转为销售单”；转换时重新校验库存，并把当时确认的商品、数量和成交价快照到销售单。
- Message 与 Inventory Privnote 保持临时展示职责。

## 10. 费用、分红与合伙人资金

### 10.1 经营费用

费用按实际付款业务日期确认：

- 工资只允许从人民币账户支付。
- 人肉费只允许从销售单记录并由人民币账户支付。
- 房租、水电和其他日常经营费用只允许从卢布账户支付。
- 表单和后端均强制上述币种规则；若未来出现不同币种的真实业务，必须先修改业务规则，不能借用“其他”分类绕过。
- 卢布费用按付款前卢布账户移动平均成本折成人民币费用。

一期提供工资、房租、水电、人肉费和其他费用分类；分类在不破坏报表口径的前提下可扩展。

### 10.2 分红

- 分红按“草稿 → 人工确认/已入账”流转；草稿可编辑，不影响资金或利润。
- 一次分红记录总额、两位合伙人的金额和各自转出人民币账户。
- 默认 50%/50%，每次允许修改；两位合伙人的金额合计必须精确等于分红总额。
- 人工确认时一次性减少对应人民币资金，并减少派生的累计未分配利润；分红不是经营费用。
- 超过确认前累计未分配利润时强警告，但内部管理账不硬性禁止。

### 10.3 投入

合伙人向公司投入资金属于权益变化，不是收入。人民币投入直接记录人民币金额；外币投入必须同时提供实际原币数量和人民币账面成本。

## 11. 对账、更正与异常

### 11.1 账户对账

账户详情显示账面余额、上次对账日期和差异状态。盘点时输入实际余额：

- 无差异则保存已核对事实。
- 有差异时优先引导补录遗漏业务。
- 确认调整时必须填写原因并生成调整流水，不能覆盖账户余额。
- 外币增加调整必须提供人民币成本；外币减少按账户移动平均成本转出。
- 启用后的无法解释资金盘盈/盘亏进入对账业务日期所在月的损益；期初调整必须按性质进入期初投入资本或期初未分配利润，不进入当月利润。

### 11.2 库存调整

破损、赠送、丢失和盘盈盘亏必须通过正式库存调整记录，不得直接修改批次数量：

- 调整必须指定原因、采购批次、库存形态（完整盒或散支）、数量、业务日期、操作人和备注。
- 破损、赠送、丢失和盘亏按指定批次调整前的剩余成本池结转，并进入业务日期所在月的库存调整损失。
- 盘盈优先归入可识别的既有批次；无法识别来源时建立独立调整批次并明确录入承接的人民币成本，该成本同时形成库存调整收益。
- 调整不得消耗已经被销售单预留的库存；可调整数量以未预留的物理库存为上限。
- 调整后必须继续满足批次数量非负、成本池非负和成本守恒。

### 11.3 更正

- 未入账草稿可编辑。
- 已入账交易通过“更正”生成反向交易和替代交易。
- 已被后续业务使用的外币交易不允许孤立更正。
- 更正保存原交易、反向交易、替代交易和原因之间的关系。

### 11.4 余额与并发保护

- 资金账户、完整盒、散支和可用库存不得为负。
- 补录交易若令任一历史时点余额为负，则拒绝入账并提示补录更早的资金来源。
- 同一库存被两位合伙人并发确认时，使用数据库行锁确保只允许一方成功预留。
- 所有写操作必须具备幂等键，网络重试或重复点击不重复记账。

## 12. 报表口径

### 12.1 月利润

```text
商品毛利
= 当月已出库商品收入
- 对应 FIFO 库存成本

经营净利润
= 商品毛利
+ 向客户收取的人肉费
- 当月实际支付的人肉费
- 工资
- 房租
- 水电
- 其他经营费用
+ 库存调整收益
- 库存调整损失
+ 资金对账收益
- 资金对账损失
```

换汇、公司账户间转账、采购付款、在途转库存、客户预收、应收转收款、合伙人投入、分红和期初余额不进入利润。

### 12.2 首页与资产

- 资金账面价值 = 人民币账户余额 + 卢布和 USDT 的人民币账面成本。
- 应收款 = 已出库未收款销售单。
- 客户预收款 = 已收款未出库订单，是履约责任而不是利润。
- 在途采购 = 已支付未入库采购的人民币成本。
- 库存成本 = 剩余完整盒与散支的人民币成本。
- 公司总资产 = 资金 + 应收款 + 在途采购 + 库存。
- 公司净资产参考值 = 公司总资产 − 客户预收款。
- 累计未分配利润 = 期初未分配利润 + 启用以来累计经营净利润 − 已确认分红。
- 累计未分配利润只从期初未分配利润、已入账损益和已确认分红派生，不另建可独立修改的余额字段。

## 13. 前端信息架构

全部新页面使用 React SPA。视觉沿用现有奶油色、勃艮第红和金色设计体系，生产 UI 必须先在 OpenDesign 项目中验证，再交由项目规定的前端代理落地。

用户界面、业务术语、设计文档和提交信息统一使用中文；Python/TypeScript 标识符、API 字段及数据库枚举使用英文。

### 13.1 全局导航

- 桌面导航新增“销售”和“账务”。
- 手机底部导航使用“品牌、库存、销售、账务、更多”；价格、链接和管理入口进入“更多”。

### 13.2 页面

1. 账务启用向导：账户、期初外币成本、切账时点库存、期初应收、预收、预留、在途和未分配利润、复核启用。
2. 账务总览：资金账面价值、库存、应收、当月利润、账户、待处理、资产构成、当月费用和快捷操作。
3. 销售中心：列表、草稿、新建、确认、出库、收款、取消、退款和生成 Privnote。
4. 资金账户：余额、移动平均、流水、对账和调整。
5. 换汇：人民币或 USDT 实际转出、卢布实际到账。
6. 采购与库存流转：采购草稿、卢布付款、在途、整单到货、拆盒和库存调整。

8. 分红：总额、两位合伙人金额和转出账户。
9. 全部流水：按日期、账户、币种、类型和操作人筛选，展示来源及更正链。

账务首页使用已批准的“总览 + 快捷操作”布局，并加入公司资产构成和当月费用分类；不在首页放六个月利润趋势。

## 14. 启用与现有数据迁移

- 切账时点固定为 2026-08-10 00:00:00（Europe/Moscow），即 2026-08-10 莫斯科日初。
- 所有期初数字必须代表切账时点之前一刻的状态。2026-08-10 当天及之后发生的资金、采购、库存和销售业务作为正式业务流水补录，不得同时包含在期初数字中。
- 即使实际盘点晚于切账日，也必须根据盘点结果和切账后业务反推、还原切账时点库存；不得直接把实施完成日的当前快照回填为 2026-08-10 期初。
- 模块完成后允许按真实业务日期补录从启用日起发生的业务。启用向导完成前，补录交易保持草稿，不产生正式余额。
- 两位合伙人填写切账时点两个人民币账户、一个卢布账户和一个 USDT 账户的期初原币余额；卢布和 USDT 同时填写人民币账面成本。
- 盘点切账时点的完整盒与散支，尽量继承现有 PurchaseBatch.unit_cost_cny；明显不可靠的成本可在启用前改为明确标记的期初估值。
- 现有 PurchaseBatch.quantity/remaining 数据转换为包装级期初库存；还原后的切账时点盘点结果是包装形态和数量的最终依据。
- 迁移必须分别识别并处理：已履约未收款、已确认未履约的库存预留、已预收未履约、已付款未到货的在途采购、期初投入资本和期初未分配利润；两种期初权益不得合并。
- Privnote 历史上自动生成但不代表真实销售的旧订单必须排除；真实销售由任一有权限的合伙人逐条人工确认后迁移，不能仅凭技术来源自动认定。
- 每个 PaymentMethod 在启用前明确映射到两个人民币资金账户之一；未映射的方法不能生成收款信息或登记收款。
- 每条迁移记录保存稳定的来源类型和来源 ID，并使用唯一约束保证幂等；迁移可以安全重跑，重复执行必须为 no-op，不得重复生成期初、预留、应收、预收或在途。
- 启用确认生成期初流水并锁定；后续修改使用更正规则。旧数据保留查询，不强制伪造缺失的历史资金和费用流水。

## 15. 测试策略

必须覆盖：

- 人民币换卢布、USDT 换卢布以及同币种转账的成本传递。
- 各外币账户独立移动平均、同日有效顺序、缓存重建顺序、余额归零尾差和负余额保护。
- 两位合伙人并发入账时系统级有效顺序不重号，且切账期初顺序先于启用日业务。
- 外币历史回填在无后续依赖时可入账、有后续依赖时被拒绝或通过受控反向与重放链处理。
- 多商品采购成本分配及尾差。
- 批次入库成本、剩余成本池、销售成本和调整成本在拆盒、销售及最后单位尾差后的成本守恒。
- 相同雪茄不同包装不能混扣。
- 完整盒 FIFO、显式拆盒和散支 FIFO。
- 草稿、确认预留、取消释放和并发预留。
- 先出库后收款、先收款后出库、整单收款金额校验、预收取消退款和退款账户余额不足。
- 销售确认后的字段冻结、所有合法状态转换及非法状态转换拒绝。
- 客户承担与公司承担人肉费时的应收及利润、确认后承担方式和收费金额冻结，以及公司承担但收费非零等非法组合拒绝。
- 人民币工资、人民币人肉费、卢布房租水电及其他费用的币种强制。
- 投入、分红草稿与确认、分配合计约束和对账调整。
- 期初投入资本与期初未分配利润同时非零时分别迁移，只有后者进入累计未分配利润。
- 破损、赠送、丢失和盘盈盘亏调整不能消耗已预留库存，并正确进入损益。
- 莫斯科业务日期的跨月边界。
- 重复提交、原子回滚、已入账不可变、反向更正和缓存重建。
- 月报损益、账户与资产汇总分别和统一流水勾稽一致。
- 2026-08-10 日初切账还原、期初流水先于当日业务、迁移重复执行幂等、稳定来源 ID，以及 Privnote 非真实旧订单排除。
- 两位合伙人的查看、记账和更正权限完全相同。
- React 桌面和手机关键流程、表单验证、空状态和错误状态。

完成实现前必须运行相应 Django 测试、前端测试与构建、迁移一致性检查，并由独立代码审查确认资金和库存不变量。
