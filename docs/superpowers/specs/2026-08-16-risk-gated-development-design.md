# 风险门禁开发流程设计

## 背景

当前项目把几乎所有代码任务都强制纳入完整 Superpowers 流程：正式 brainstorming、计划文件、worktree、TDD、多轮审查以及反复全量验证。该方式对高风险会计和数据迁移有价值，但用于文案、样式、类型修复和普通功能时，流程成本明显高于开发成本，并造成长时间运行、大量上下文重复和过高 token 消耗。

新的流程不取消测试、审查或 CI，而是让投入与业务风险匹配。

## 核心原则

采用“风险门禁开发”（Risk-Gated Delivery）：

> 直接实现是默认；设计、测试、审查和验证成本必须与变更风险匹配。

主代理自动判断风险等级并继续推进。只有不可逆操作、生产数据修改或缺少关键业务决定时才请求用户确认。

## 风险等级

### 低风险

包括文案、样式、帮助内容、小型配置、明确的类型修复和局部无状态 UI 调整。

- 在当前干净分支直接修改。
- 不要求正式 spec、plan、worktree 或独立 reviewer。
- 使用类型检查、Lint、构建或页面冒烟等最小充分验证。

### 中风险

包括普通前后端功能、API 契约调整、跨文件状态行为和可恢复的数据写入。

- 在对话中记录 5–10 行需求契约：目标、非目标、影响范围和验收标准。
- 直接实现，不执行 RED→GREEN。
- 实现后补关键行为测试。
- 完成后进行一次独立审查。

### 高风险

包括会计金额、汇率、成本、利润、库存数量、订单状态、权限、幂等写入、数据迁移和 production 部署。

- 业务规则不明确时先完成正式设计。
- 使用 feature branch；并行、长期或实验性工作才创建 worktree。
- 实现后验证关键不变量和错误路径。
- 合并前进行独立审查；只修复 Critical 和与当前需求相关的 Important。
- 不可逆操作和生产数据变更必须获得用户确认。

## 默认开发流程

```text
需求契约
→ 影响范围扫描
→ 直接实现
→ 目标验证
→ 按风险审查
→ CI 全量验证
→ 合并或部署
```

普通任务不再强制生成或提交 spec、implementation plan。只有新增领域模型、改变会计规则、跨多个子系统或涉及不可逆数据时，才创建正式设计文档。

## 测试策略

取消强制 TDD 和 RED→GREEN。允许先实现，再验证和补测试。

实现后必须测试：

- 会计金额、汇率、成本、利润和库存数量的不变量。
- 订单、采购、出库、收付款等状态流转。
- 已实际发生过的 Bug 回归。
- 数据解析、权限判断和幂等写入。
- 数据迁移与不可逆操作。

默认不写单元测试：

- 纯排版、颜色和文案。
- 简单组件拼装。
- 框架本身已经保证的行为。
- 已由 TypeScript、Lint 或构建可靠覆盖的问题。
- 为了测试而必须大量拆分生产代码的实现细节。

开发期间只运行受影响测试。完整前后端测试主要由 CI 执行一次；只有高风险任务才要求本地额外全量验证。

## 审查策略

- 低风险：主代理自审。
- 中风险：完成后一次独立审查。
- 高风险：允许实现期间并行审查，合并前再做一次最终审查。
- 修复反馈后只复审受影响区域，不重新审查整个代码库。
- Minor 和无关历史问题记录为技术债，不扩大当前任务。
- 审查新增工作超过原范围约 30% 时，先向用户汇报。

Subagent 可以积极用于并行调查、独立模块实现和集中审查，但不再为每个小步骤串行派发新代理。

## Git 与交付

- 低风险任务可在当前干净分支直接提交。
- 中高风险任务使用 feature branch。
- worktree 仅用于并行、长期或实验性工作。
- 保护用户未提交改动，禁止擅自 stash 或覆盖。
- 默认不 push；只有用户明确要求才 push。
- 本地进行目标验证，完整验证交给 CI。
- production 只部署通过 CI 的准确提交 SHA。

## 效率约束

- 预计 30 分钟内的任务不写正式计划。
- 相同代码未变化时不重复运行同一套全量测试。
- 一项审查不自动引入无关历史重构。
- 进度只在里程碑汇报，不持续输出测试轮询过程。
- 连续两次修复无效时升级为系统化诊断。
- 自动选择 subagent 数量和模型，以并行收益为准，不人为限制正常委派。

## 对现有规则的影响

实施时需要重写 AGENTS.md 的以下冲突规则：

- 删除“任何代码任务必须完整执行 Superpowers 流程”。
- 删除“所有修改必须 TDD”。
- 取消普通任务强制 spec、plan、feature branch 和 worktree。
- 将 requesting-code-review 和 verification-before-completion 改为风险触发。
- 保留数据安全、禁止覆盖用户改动、禁止擅自 push、前端 React SPA、生产部署和项目领域规则。

Superpowers 技能仍可按需调用，但不再作为所有代码任务的强制流水线。

## 验收标准

- Agent 能自动给任务分级并直接推进。
- 普通任务不再被 TDD、计划文件和多轮全量验证阻塞。
- 会计、库存、资金、权限、迁移和部署仍有明确安全门禁。
- CI 成为完整测试的主要执行位置。
- 审查不再无限扩张当前任务范围。
- 用户仍保留对 push、不可逆操作和生产数据变更的最终控制权。
