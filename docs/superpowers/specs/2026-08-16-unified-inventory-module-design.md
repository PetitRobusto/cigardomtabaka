# 统一库存 Module 第一阶段设计

**状态：** 已确认，进入实现
**范围：** 后端库存写入边界；不新增页面，不实现退货、预售分配或入库撤销

## 目标

建立一个统一库存 Module，使 Day 1、采购入库、销售预留、释放、出库、库存调整和拆盒共享同一写入 Interface。调用方不再直接协调 `PurchaseBatch`、`StockAllocation` 与 `StockMovement`。

## 不变量

- `StockMovement` 是追加式库存事实；创建后不得修改或删除。
- `StockAllocation` 的销售明细、采购批次和数量创建后不可修改；状态只能按 `reserved → fulfilled` 或 `reserved → released` 流转。
- `PurchaseBatch` 的来源、数量、包装形态和成本字段只能在受控库存写入作用域内创建或修改。
- 每个库存动作同时更新库存流水与批次读模型；任一步失败时整笔事务回滚。
- 预留和释放只改变可售库存，不改变物理库存和成本池。
- 出库减少物理库存与成本池，并把成本转入累计销售成本。
- 拆盒只改变完整盒/散支形态，不改变总支数和成本。
- 采购入库、Day 1 期初和正向调整建立的批次必须同时创建对应库存流水。

## Module Interface

库存 Module 提供七类内部业务动作：

1. `open_stock`：仅供 Day 1 确认建立期初批次和 opening 流水。
2. `receive_stock`：供采购整单到货建立采购批次和 receive 流水。
3. `reserve_order_item`：按包装形态和 FIFO 为单条现货销售明细预留库存。
4. `release_order`：释放一张未出库销售单的全部活动预留。
5. `ship_order`：把一张销售单的完整预留转为出库，并返回精确 FIFO 成本。
6. `adjust_stock`：执行正向或负向库存调整，返回会计入账所需成本结果。
7. `split_box`：把一个可用完整盒转换为同批次散支。

业务命令仍负责订单状态、采购状态和会计分录。库存 Module 只拥有批次、库存分配和库存流水；调用方必须在同一数据库事务内完成其余业务事实。

## 受控写入

模型写保护使用独立的库存作用域，不复用账务作用域：两者保护的事实不同，并且采购到货、出库和调整会在同一事务中同时使用两种作用域。

- 普通业务代码直接 `create`、`save`、`update`、`bulk_create`、`bulk_update` 或 `delete` 库存事实时抛出异常。
- 库存 Module 以明确动作原因、真实操作人和字段白名单开启作用域。
- Django migration 使用历史模型，不受运行时模型保护影响。
- 专门的数据修复必须显式调用内部修复入口；第一阶段不提供普通业务可调用的修复后门。

## 兼容与后续范围

- 现有公开业务命令与 Agent Interface 保持兼容，只把内部库存写入委托给新 Module。
- 第一阶段不改变当前销售单对预售明细的处理；“一张销售单不得混合现货和预售”的新规则在预售分配阶段一并落实，并届时更新 `CONTEXT.md` 与 ADR-0014。
- 撤销整单入库、预售整单分配/释放、整单退货、撤销调整和全量一致性审计属于第二阶段。
- 页面入口和完整 Help 场景说明属于第三阶段。

## 验证

- 模型门禁测试：所有普通 ORM 写入路径均被拒绝，合法库存动作可写入。
- 库存动作测试：opening、receive、reserve、release、ship、adjust、split 的数量、包装形态与成本不变量。
- 回归测试：Day 1、采购、销售工作流、出库会计、Agent 库存命令。
- 独立审查：实现期间检查一次，合并前再检查 Critical 与当前范围 Important。
