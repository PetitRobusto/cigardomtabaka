# 内部通知模块设计草案

状态：第一版实现完成并通过本地验证，尚未部署。

## 已确认范围

- Telegram 为当前通知渠道，接收者仅为负责人和内部人员，不向客户发送通知。
- 内部人员有固定 Telegram ID，用于限定接收范围。
- 已复用用户本人通过 BotFather 创建的 `@moscow_cigar_bot`；Bot 已能访问负责人私聊和内部业务群。
- 通知需求包括故障告警、发货通知、收款通知和 Privnote 付款截图上传通知；其他事件逐项确认。

## 已确认通知分工

- 内部群接收业务通知：待出库提醒、出库成功、正式收款成功、付款凭证已提交、已确认订单取消。
- 负责人私聊接收系统故障；Telegram 投递本身最终失败时只记服务器日志，避免递归告警。
- 群消息可见范围由 Telegram 群成员决定，个人接收 ID 白名单不能限制其他群成员阅读。
- Telegram 本身不可用时，同渠道告警也可能无法送达；最终失败记录日志，不保证恢复后补报。发送失败告警不得递归产生新的发送失败告警。

## 已确认的履约通知

- 同时需要“待出库提醒”和“出库成功通知”，分别服务于安排发货和同步完成结果。
- 大部分订单为全现货订单；全现货订单确认成功后立即触发待出库提醒，不要求先收款。
- 正式收款成功时单独发送收款通知；付款凭证上传仍是独立的待核实通知。
- 纯预售和混合订单第一版不发送待出库提醒，也不提供定时催办。
- 出库成功通知对应正式出库事实。
- 已确认订单取消成功后向群发送取消通知，提醒停止按此前待出库消息安排发货；未确认草稿的取消或删除不通知。
- 第一版不发送退货成功、退款成功通知。群消息并非完整的订单状态记录，最新状态以网站为准。

## 已确认的付款凭证通知内容

- 客户上传付款凭证后，向内部群发送付款截图以及摘要，不仅发送后台查看链接。
- 摘要包括订单号、客户名称、截图数量、待核实提示和后台查看链接。
- 消息明确标注待核实；不能将客户上传截图表述为正式收款成功。
- 付款截图会被复制到 Telegram 群，群成员可以查看和保存；系统内附件的访问控制或删除不会自动作用于 Telegram 副本。
- 摘要先作为文本消息发送，图片逐张上传；每次上传独立重试，允许部分图片最终发送失败。

## 已确认的投递取舍

- 优先简单，不引入消息队列、消息代理或持久化待发送表。
- 发送失败只做有限次重试，次数和超时预算待细化；最终失败记录日志并放弃，不做恢复后补发。
- 接受通知丢失，包括重试耗尽或发送期间进程退出。Telegram 通知不作为业务事实来源。
- 不再采用此前提出的可靠留存、持续补发方案。
- 每次 Telegram API 调用最多尝试 3 次，连接超时 2 秒、响应超时 5 秒；发送任务使用每个 Gunicorn 进程最多 4 个 daemon 线程，槽位满时记录日志并放弃。

## 已确认的交互边界

- Telegram 仅提供通知及网站跳转链接，不接收核实收款、出库等业务操作。
- 正式业务动作继续在网站执行，沿用网站身份验证、权限、审计和幂等规则；Telegram ID 不作为网站登录凭据。
- 跳转工作人员页面仍需网站登录，不通过链接附带凭据或绕过权限。
- 本模块无需为了通知接收 Bot 命令或按钮回调；现有 Bot 只用于这套内部通知。

## 已确认的第一版故障范围

- 覆盖生产 Django 的 HTTP 500、未捕获异常和明确记录的严重应用错误。
- 正常业务拒绝，例如库存不足或参数校验失败，不作为故障告警发送。
- 异常诊断详情脱敏后保留在服务器，Telegram 向负责人私聊发送摘要与定位信息。
- 第一版不包含整站宕机、服务器断网等外部可用性监测；后续需要时单独接入。
- 相同异常按日志来源、异常类型、代码位置和请求路径生成指纹；每个 Gunicorn 进程 5 分钟内只通知一次。多个进程仍可能各发一次。

## 现有业务语义

依照 CONTEXT.md：付款凭证提交不等于正式收款；工作人员核实并生成正式收款事实后，才算已收款。现有出库动作表示系统履约事实，不能据此推断物流已经揽收。

现有确认动作允许纯预售或混合销售单进入 confirmed 状态，但只预留现货；现有整单出库动作拒绝含预售明细的订单。因此不能仅凭 confirmed 状态就推断整单可以出库。履约与收款状态独立，现有出库服务允许已确认、未收款订单出库。

## 实现原则

- 将业务事件与 Telegram 投递分开，由通知模块统一处理路由、消息格式、去重与重试。
- 业务通知只对应已提交的事实；通知投递失败不改变业务执行结果。

## 第一版实现决定

- 直接使用项目已有的 `requests` 调用 Telegram Bot API，不引入 Apprise、GlitchTip、Sentry 或新的服务。当前只有一个渠道且已接受尽力投递，引入通用通知框架或错误平台的运维成本大于收益。
- 业务服务在事务内生成不含 ORM 延迟读取的消息快照，通过 `transaction.on_commit()` 提交发送；回滚不发送。
- 全现货订单确认后发送待出库提醒；纯预售和混合订单第一版不发送待出库提醒，避免把不可整单出库的订单提示为可发货。
- 出库、正式收款和已确认订单取消只在新业务事实创建时安排通知，幂等重放不重复通知。
- 付款凭证只在新提交创建后安排通知，幂等重放不重复发送截图。
- 固定目标在 settings 中使用已核实的业务群 ID `-1003900174592` 和负责人 ID `8206776258`，也可用环境变量 `TELEGRAM_BUSINESS_CHAT_ID`、`TELEGRAM_ERROR_CHAT_ID` 紧急覆盖；Bot Token 仅由部署环境的 `TELEGRAM_BOT_TOKEN` 提供，禁止进入仓库。

## 后续版本候选

- 纯预售和混合订单的专用待办提醒。
- 外部整站可用性监测。
- 退货、退款通知。
